# 1113 MLSYS 特辑 · 上下文太长：分层存，还是压成向量？

## 评论

长程 Agent 的上下文越积越长，这些状态该怎么放？三篇新论文给出两条路：两篇保留全量状态，只改变它放在哪一层、留哪几个恢复点；一篇把工具返回压成一百多个连续向量。判断走哪条路，先问这些内容以后还会不会被原样用到。

## 本期重点

**HiState**（加州大学圣地亚哥分校）针对注意力层加循环层的混合模型。注意力缓存按 token 存，可以截断复用；循环状态是整段前缀的摘要，只能从留过检查点的位置恢复。普通对话只往后追加，在每轮结尾留一个检查点就够了；Agent 会把长消息从中间截短，也会退回某一步改掉输入再重跑，复用点于是落在没有检查点的位置。把检查点打密又会挤占注意力缓存：论文的例子是 32K token 上下文、每 1,024 个 token 一个检查点，循环状态约 1.6 GB，同一段上下文的 KV 约 1.1 GB。HiState 利用「恢复一次要读全部注意力缓存、却只读一个检查点」的不对称，把快内存留给注意力缓存，历史检查点放到 SSD；按作者的估算，从 SSD 读一个检查点只比从内存多约 10 毫秒，而 32K token 的 KV 挪到 SSD 后加载要从 16.8 毫秒涨到 231.5 毫秒。此外还有自适应的检查点间隔和把两类状态统一排序的淘汰策略。在 vLLM 上实现、回放 Weka 与 TraceLab 两份公开的编程 Agent 轨迹（Qwen3.5-9B，单张 H100）：相对只在轮次边界留检查点、缓存只在显卡上的 vLLM-Marconi，p99 首 token 延迟加速最多 5.73 倍，相对 SGLang-HiCache 最多 5.44 倍；相对同样使用内存和硬盘的 vLLM 扩展基线，复用敏感请求的平均首 token 延迟在 Weka 上从 2.66 秒降到 1.29 秒。

**Adaptive DHiSparse**（Umans AI）面向稀疏注意力的长上下文模型：每个查询先由索引器从历史里选出一小部分条目，只对它们做注意力。前作 HiSparse 把完整历史放在主机内存，显卡只留固定大小的热缓存，缺的条目按需取回。这一篇补了两个缺口。其一，驻留量随负载伸缩：只保护一个很小的必需工作集，显存有富余时多留历史，别的请求需要时收回；负载阶跃实验里，低负载时需要回主机取的条目从 14.2% 降到 1.4%。其二，让 DFlash2、DSpark 这类并行草稿的投机解码在分层缓存上工作：一轮验证里的多个查询合并取数，草稿 KV 只保留一个固定窗口，验证暂存跨层复用，每个会话只多占 0.060 GiB 显存。100K 上下文下，每个会话必须驻留的显存是 0.432 GiB，全量驻留是 4.444 GiB。GLM-5.3、100K 上下文、128 并发时，每张解码显卡每秒输出 793 个 token，是 HiSparse 的 1.45 倍、不开投机解码时的 1.27 倍；按 HiSparse 的延迟上限来卡，可承载的并发最多是 4 倍。并发很低、历史全部放得进显存时，全量驻留反而快 5% 到 7%。

**Coca-Cola**（清华大学）质疑「工具返回必须以文本进入上下文」这个默认前提：一个搜索 Agent 走到第四步时，上下文里 96.7% 的 token 是工具返回。它用一个轻量编码器把每次工具返回压成 128 个连续向量，直接放进 Agent 的输入嵌入空间。训练目标不是还原原文，而是让 Agent 读压缩向量时的下一步动作分布贴近读完整原文时的分布；Agent 本身冻结，只训练压缩器，压缩器同时读任务目标和当前的推理状态。在 NQ、TriviaQA、2WikiMultiHopQA、HotpotQA 四个网页搜索问答数据集、两组模型上，总 token 消耗减少 70.01% 到 89.24%，端到端运行时间减少 24.45% 到 55.97%，EM 和 F1 在全部设置里都高于不压缩的 Agent；同样结构改用还原原文训练（ICAE），八组设置里压缩率都更低。

合起来看：分层存放不改变模型看到的内容，赌的是访问有局部性、慢的那一层足够便宜；压成向量省得更多，但信息按当时那一步的决策筛过，丢掉的找不回来，压缩器也是针对特定 Agent 模型训练的。

## 制作元信息

- 三篇都是 arXiv 预印本，均未声明会议或期刊录用；数字全部取自论文 v1 正文。
- HiState 的 5.73 倍对比的是缓存只在显卡上的基线；仅靠把缓存卸载到内存和硬盘，尾延迟就已大幅下降。复用敏感请求约占全部请求的 1%（TraceLab 4,791 个请求中 46 个），p50 首 token 延迟与使用硬盘的基线大致持平、在 Weka 上略有回退。实验只用了一个模型、一张显卡；使用内存和硬盘的 vLLM 基线是作者自己的扩展实现。
- Adaptive DHiSparse 用的是固定输入长度、预先准备好前缀的闭环压测，不是真实 Agent 轨迹；并发升到 256、会话槽位占满后，投机解码不再增加输出（826 对 823 token/s）；验证块大小是按并发手工设定的。节目里的「自适应分层缓存」是我们的口头简称。
- Coca-Cola 只在网页搜索问答上验证；代码执行、文件读取这类返回细节之后还会被引用的工具，论文没有测。压缩器需要访问 Agent 的输入嵌入层并针对该模型训练。
- 节目里「连续向量没有 token 编号，如何与前缀缓存配合」的问题，以及结尾的判断，是主持人的看法，不是论文结论。
