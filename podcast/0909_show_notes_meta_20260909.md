0909 MLSYS 论文简报：加速的保证，谁来验

今天三篇都在讲加速，而且都在投机解码和早退这条线上。三篇的加速数字都挺实在，但读到最后会发现一件事：三篇里最关键的那句承诺——加速不要钱——都是论证出来的，不是测出来的。

第一篇，批量禁区（俄亥俄州立 / 微软研究院 / 密歇根大学，arXiv:2608.24004）。投机解码的思路很朴素：让便宜的东西先猜几个 token，大模型一次性验证，猜对白赚。单条请求上很好用，批量为 1 时主流方法能到 2.5 倍以上。但生产环境是一大批一起跑，而这篇测出来的比预想的严重得多——不是收益变小，是变成负的：批量超过 32 之后，投机解码比什么都不做还慢；默认批量 256 下，它测的 12 个格子里有 11 个 baseline 等于或低于 1 倍，最差掉到 0.45 倍。原因它也测清楚了：一是猜错太多，agent 负载上几个主流方法的拒绝率是 53%、66%、89%，而每个被拒绝的猜测大模型都已经花算力验证过；二是批量 256 正好吃满这张卡的算力，验证一个 token 的成本已逼近正常吐一个 token，白赚的前提没有了。它的解法是不用额外模型，只从这个请求自己的历史里找草稿——但关键在于，它发现 agent 的重复几乎只发生在同一查询的同一语义块内部（一段代码块、一次工具调用），于是只从当前块的历史里取，拒绝率压到 26%，最好的格子拿到 2.02 倍。问题有两个：它说自己无损，可全文没有一个质量数字，只有一句"不打算改变输出分布"——那是意图不是测量；而它端到端只测到 256，恰恰是它自己公式说预算已归零的那一点，再往上是负的，而它另一张剖析图一直画到 1024。

第二篇，长上下文禁区（香港科技大学广州，arXiv:2608.30252）。这里有个漂亮的矛盾：你想让草稿猜得准，草稿就得看见上下文；可它一旦看见，自己也要存一份 KV——32K 上下文下草稿额外要 17.21 GB，你省的显存又被草稿吃回去了。它把草稿的 KV 换成一份紧凑工作记忆：开头 128 个锚点保留原样、最近 128 个滑动窗口保留原样、中间每若干 token 压成一个记忆槽。记忆槽是学出来的，是全方案唯一需要训练的部分，草稿骨干冻结；训练目标不是让槽去"概括"被丢掉的内容，而是在预测下一个 token 这件事上功能性地替代它们。结果：草稿显存 17.21 GB → 3.98 GB，草稿延迟 41 毫秒 → 12 毫秒，每轮接受 token 从 4.05 掉到 3.43，而且代价是次线性的，再压一倍几乎不再掉。为什么压草稿是安全的，它论证得很漂亮：目标模型的 KV 完整保留，验证仍是标准接受拒绝规则，所以草稿压坏了最多是接受率下降，不会让结果出错。但同样没测——没有输出一致性检验，而且全部实验是贪心解码温度为零，恰恰避开了唯一会真正考验那条规则的采样场景。

第三篇，早退（苏州大学，arXiv:2608.27963），跟前天那期直接接上。它盯着模型吐出"等一下"的时刻，把推理分成两支：一支中性，让它直接给答案；一支挑衅，跟它说你前面错了、改正后答案是什么。如果被这么一激答案还不变，说明结论已经稳了就收。这个"对抗"其实就是一句提示词，便宜又聪明。数字是推理 token 少 30.2%，准确率还从 67.8 涨到 69.0。但要看它量的是什么：它报的是推理阶段的 token，不是总量，作答阶段一个字没算——而前天那篇论文的发现正是泄漏发生在作答阶段。任何越过标记继续写的推理，都会被自动归类成"答案"，从这个数字里消失。另外探测本身要花 183 个 token，也没从省下的里面扣，扣掉后是 26.5% 到 37.5%。它有一点很诚实：自己的消融承认收益主要来自两支对照这个框架，而不是它命名的那个稳定性公式。

三篇都把加速推到了原本会垮的地方并各自救了回来。但那句"不要钱"，三篇都没验：第一篇说无损却没有一个质量数字，第二篇的论证很漂亮但只在贪心下跑，第三篇的"省下来"只算了看得见的那一半。共同点是，验证的成本其实都不高——一次输出一致性检查、一组带温度的采样、一个总 token 的计数。难的是做完之后，数字可能就没那么好看了。一个方法说自己没有代价的时候，那句话往往是全文最需要被测量、却最少被测量的一句。
